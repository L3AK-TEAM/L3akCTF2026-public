## admin

The first thing to look at is `/api/register`. Our body gets parsed once with `json` then again with `ujson`:

```python
payload = json.loads(raw)
if payload.get("role", "user") == "admin":
    return jsonify({"error": "self-service accounts cannot request the admin role"}), 403

record = ujson.loads(raw)
role = record.get("role", "user")
session["role"] = role
```

So the value that is checked at the beggining is not necessarily the value that ends up in the session. The installed `ujson` version is `5.0.0` and all it takes is a dangling surrogate to make the 2 parsers disagree:

```json
{"username":"cea","password":"cea","role":"admin\ud887"}
```

`json` keeps the broken character, meaning the value is not `admin` and the check passes fine. But `ujson` drops that part and gives us `admin`. So `/api/me` should now returns the admin role.

## ssrf

With admin we can use the manifest importer. It has the same problem logic but this time with URL parsing:

```python
mirror = urllib.parse.urlparse(url).hostname
if mirror not in TRUSTED_MIRRORS:
    return jsonify({"error": "mirror is not on the trusted list"}), 403

resp = requests.get(url, timeout=5, allow_redirects=False)
```

The URL we can use is as the following:

```text
http://127.0.0.1:8000\@manifests.buildfarm.internal/x?spec=...
```

For `urllib.parse`, the host will be `manifests.buildfarm.internal` which is allowed. But `requests` sees it differently and connects to `127.0.0.1:8000` instead. And this is the internal worker (which is running as root).

Now take a look at what happens to build environment variables:

```python
resolved[key] = string.Template(val).safe_substitute(VAULT)
proc = spawn([sys.executable, "-I", RUNNER, "build", workdir, str(ttl)], child_env, workdir)
```

The first clear choice is "Env to RCE", but there was not much to use (ig, idk if someone managed to solve it with that, if yes share it with me plz :p). The dangerous variable’s names are filtered, python is run with argument -I and the runner itself only writes the log and does nothing else after that.

The key here is safe_substitute(VAULT). Sending `"FLAG":"${FLAG}"` means that the worker puts the original flag into the runner’s environment for us. The solution uses the manifest:

```json
{
  "task": "build",
  "ttl": 90,
  "env": {
    "FLAG": "${FLAG}",
    ...
  }
}
```

Well the big TTL is just to keep the runner alive.

## reading files

The app has this endpoint:

```python
path = os.path.join(WORK, target)
return send_file(path)
```

There is no check after the join, and `WORK` is `/work`, so one `..` gets us out:

```text
/download/%2e%2e/etc/passwd
```

You can also access the `/proc` files from here. The PID of the runner generated by our manifest is the important piece of information, which can be read from `/proc//cwd/build.log`, as we have to check which logs contain the static buildfarm strings.
At this point the straight solution looks like:

```text
/download/%2e%2e/proc/<runner-pid>/environ
```

The flag is in that file and the app can read it. BUT the response body is empty. It even returns `200` which is a bit confusing at first.

The reason is not the LFI but `/proc/<pid>/environ` is a special procfs file and `stat()` reports its size as `0`. Werkzeug trusts that size. Btw these are the lines that u might want to check in [`send_file()`](https://github.com/pallets/werkzeug/blob/2.2.3/src/werkzeug/utils.py#L440-L504):

```python
stat = os.stat(path)
size = stat.st_size

# some code later
file = open(path, "rb")
data = wrap_file(environ, file)

if size is not None:
    rv.content_length = size
```

The file opens but `size` is saved as 0 and becomes the response `Content-Length`. That's why just asking for `environ` doesn't get us anywhere.
But it also gives us the race idea. `stat()` and `open()` are not a single operation. If `stat()` sees a normal file, but then `open()` sees `environ`, we have a valid size with the data we want. The only missing piece is a path that can change between those calls.

## fd race

`/proc/self/fd/` is a directory that has entries that are symlinks to the file that is currently utilizing the file descriptor. If file descriptor `13` is currently having `/etc/passwd`, then `/proc/self/fd/13` will have that location, and if it is deleted, linux will reuse the descriptor `13` for another file.

`self` in this case is important too since it refers to the flask app that is processing all requests for downloads and not the runner. The PID for the runner has only been used to determine the path for `environ.` 

The solve keeps making these requests:

- 4 threads request `/etc/passwd`. This gives us open FDs pointing to a regular file with a real size. (A)
- 4 threads request `/proc/<runner-pid>/environ`.
- 10 reader threads request `/proc/self/fd/<n>` and look for `L3AK{...}`.

The mentioned nums are just the default values in the script. Before activating the readers, it checks all the file descriptors from `13` to `80`. If any of the file descriptors return `root:x:0:0`, it indicates that it has returned somewhere within range of the request (A).

For one successful request, the order should be:

1. FD `13` points to `/etc/passwd` when the reader reaches `stat()`. We now have a non-zero size.
2. The FD gets closed and reused for the runner's `environ`.
3. The same reader reaches `open("/proc/self/fd/13")`, but the symlink has changed already.
4. Werkzeug sends bytes from `environ` using the size it got from `/etc/passwd`.

Btw using larger files in place of `/etc/passwd` would be better, like a `.so` file or whatever in the container there, and then the rest is just retrying the race.
